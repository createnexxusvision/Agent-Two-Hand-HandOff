# Deploying to Render

`render.yaml` creates three things in one region (Oregon):

| Resource | Name | What it does |
|---|---|---|
| Web service | `agent-two-hand-handoff` | The demo site, approvals, the PayPal webhook endpoint, the ledger download |
| Workflow | `handoff-workflows` | Render Workflows tasks: plan, deliver and verify (in parallel), decide, settle |
| Postgres | `handoff-db` | Append-only receipts, payout jobs, encrypted payee addresses |

## Before you start

1. **A Render API key**, so the web app can start workflow runs: Render Dashboard → your avatar → **Account Settings** → **API Keys** → **Create API Key**. Keep it somewhere private for step 3. (Optional: without it, every step runs inside the web service instead.)
2. **Your sandbox values**, the same ones in your local `.env`: PayPal Client ID and Secret, the two sandbox payee emails, and the Google AI key.

## Steps

1. Render Dashboard → **New** → **Blueprint** → pick `Agent-Two-Hand-HandOff` → branch `main`.
2. Render reads `render.yaml` and lists the web service, the workflow, the database and the `handoff-shared` environment group. Check the plans and prices it shows before going on.
3. Render asks for each secret marked `sync: false`. Paste them here, in Render's form, never in chat or in git:
   - `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`
   - `GATE_PAYEE_EMAIL_1`, `GATE_PAYEE_EMAIL_2` (the sandbox personal accounts that play Theo and Ana)
   - `GOOGLE_GENERATIVE_AI_API_KEY`
   - `RENDER_API_KEY` (from "Before you start")
4. Click **Apply**. The first deploy installs, builds and starts everything. `TRUST_MASTER_KEY` and `TRUST_SIGNING_SEED` are generated by Render; do not change them later, or stored addresses and existing signatures stop matching.
5. Open `https://<your-service>.onrender.com/api/health`. Expect `"ok": true`, `"paypal": true`, `"ai": "google"` and `"runs": "render-workflows"`.
6. Check the workflow slug: Render Dashboard → `handoff-workflows` → **Tasks** → open `demoWeek`. Its slug is shown as `<slug>/demoWeek`. If the slug is not `handoff-workflows`, change `HANDOFF_WORKFLOW_SLUG` in the `handoff-shared` group to match.

## Register the PayPal webhook (gate 2)

1. developer.paypal.com → Apps & Credentials (**Sandbox**) → your app → **Webhooks** → **Add Webhook**.
2. URL: `https://<your-service>.onrender.com/api/webhooks/paypal`.
3. Events: all `PAYMENT.PAYOUTS-ITEM.*` events, the three `PAYMENT.PAYOUTSBATCH.*` events, and `INVOICING.INVOICE.PAID`.
4. Copy the new **Webhook ID**. Add it as `PAYPAL_WEBHOOK_ID` on the web service in Render (Environment → Add) and in your local `.env`. The service redeploys.
5. Run a demo week on the live site. Receipts marked `verified by PayPal` came through the webhook; `status read from the PayPal API` came from polling, which stays on as the fallback.

## How the work is split

| Step | Where it runs | Why |
|---|---|---|
| Sign the mandate | Web request | Fast, and rate-limited per demo |
| Plan tasks (ops agent) | Workflow task `planTasks` | Model calls retry with backoff (Gemini can be busy); falls back to a scripted plan after the retries |
| Deliver and verify | Workflow task `deliverAndVerify`, one run per task, in parallel | Each verification has its own retry boundary and shows as its own run |
| Decide | Workflow task `decide` | Plain code; retried if the database blips |
| Pay and follow to settlement | Workflow task `settle` (up to 15 minutes) | Survives web redeploys; polls PayPal until every item settles, then seals a checkpoint |
| Approvals, webhooks, ledger | Web service | Need a person or an inbound HTTPS request |

Every step is safe to retry: state is rebuilt from receipts, jobs are claimed with `SKIP LOCKED`, and the PayPal batch id is derived from the decisions, so a retried pay run cannot pay twice. If the Render API is unreachable, the web service runs the same steps in-process.
